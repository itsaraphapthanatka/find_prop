3. ผู้ใช้ การล็อกอิน และสิทธิ์

3.1 วิธีเข้าสู่ระบบ

  • อีเมล + รหัสผ่าน — สมัครเองได้ (self-serve) ถ้าเปิดยืนยันอีเมลไว้ Supabase จะส่งลิงก์ยืนยันก่อนใช้งาน
  • Google OAuth (PKCE) — บนเว็บ redirect กลับหน้าเดิมอัตโนมัติ · ในแอปเปิด in-app browser แล้วรับ deep link com.hobproperty.app://auth-callback มาแลก session เอง

สมัครแล้วระบบสร้างแถวใน profiles อัตโนมัติ (trigger ที่ auth.users) จากนั้นผู้ใช้ตั้งชื่อองค์กรของตัวเอง → ได้เป็นแอดมินขององค์กรนั้น

3.2 ล็อกอินได้ทีละเครื่อง (single device login)

ล็อกอินสำเร็จ→ สุ่มรหัสประจำเครื่องเก็บ localStorage→ จดลง profiles.current_session_id (RPC)→ เครื่องเก่าเห็นรหัสไม่ตรง → เด้งออก
  • เครื่องเก่ารู้ตัวผ่าน Realtime ทันที + เช็คซ้ำทุก 60 วินาที + ตอนสลับกลับมาที่แท็บ/แอป
  • หลายแท็บบนเครื่องเดียวกันใช้รหัสเดียวกัน — ไม่เด้งกันเอง
  • โค้ด: src/lib/deviceSession.ts · ฐานข้อมูล: supabase/single-device.sql

3.3 บทบาท (role) — 8 ระดับต่อองค์กร + super

super คือทีมงาน HOP (ไม่มีสังกัดองค์กร) — เห็นทุกองค์กร จัดการแพ็กเกจ/ราคา/ตั้งค่าระบบ และสวมสิทธิ์ (impersonate) เข้าองค์กรใดก็ได้ · ส่วนบทบาทภายในองค์กรมี 8 ระดับ (ของเดิม admin → owner, member → manager โดยไม่มีใครเสียสิทธิ์):

บทบาทเห็นทรัพย์ติดต่อเจ้าของพิกัด/แผนที่แก้/ลบของคนอื่นนำออก Excel
owner เจ้าขององค์กรทั้งองค์กรเห็นเห็นได้ทั้งหมด + จัดการทีม/แพ็กเกจได้
manager ผู้จัดการทั้งองค์กรเห็นเห็นแก้ได้ · ลบได้ยกเว้นทรัพย์ที่ owner ลง—
associate นายหน้าร่วมทั้งองค์กรปิดเห็น——
analyst นักวิเคราะห์ทั้งองค์กรปิดปิด——
survey ทีมสำรวจทั้งองค์กรปิดเฉพาะเขตที่กำหนด——
temporary ชั่วคราวเฉพาะเขตที่กำหนดปิดเฉพาะเขตที่กำหนด——
social ดูแลโซเชียลทั้งองค์กรปิดปิดดูอย่างเดียว (read-only)—
trainee ฝึกงานเฉพาะที่ตัวเองลงเห็น (ของตัวเอง)เห็น——
  • ทุกบทบาทเห็น/แก้/ลบ "ทรัพย์ที่ตัวเองลง" ได้เสมอ ยกเว้น social (ดูอย่างเดียวทั้งระบบ)
  • ดูประวัติการใช้งาน (Logs) ได้เฉพาะ owner และ manager
  • เขตที่กำหนด (survey/temporary): กำหนดเป็นรายจังหวัด หรือจังหวัด+เขต/อำเภอ ต่อสมาชิก (ตาราง member_areas — ไม่กำหนดเลย = ไม่เห็นเขตใด ปิดไว้ก่อนปลอดภัยกว่า)
  • ตรรกะสิทธิ์เขียนคู่กัน 2 ที่: src/lib/roles.ts (ซ่อน/ปิดปุ่มใน UI) และ supabase/roles.sql (ด่านบังคับจริงในฐานข้อมูล)
  • สมาชิกมีเบอร์โทรในโปรไฟล์ (profiles.phone) — ให้บทบาทที่ถูกปิดข้อมูลเจ้าของติดต่อ "คนลงข้อมูล" แทนได้

4. องค์กรและ Multi-tenant

  • ทุกข้อมูลผูกกับ org_id — RLS บังคับว่าสมาชิกเห็นเฉพาะข้อมูลองค์กรตัวเอง (1 องค์กร = 1 ทีมลูกค้า)
  • ผู้ใช้หนึ่งคนเป็นสมาชิกได้หลายองค์กร (ตาราง memberships) และสลับองค์กรที่ใช้งานได้จากเมนู (RPC switch_org)
  • สถานะองค์กร: ใช้งานได้เมื่อไม่ถูกระงับ (sub_status ≠ suspended) + แพ็กเกจไม่หมดอายุ + ช่วงทดลองไม่หมด — ตรรกะเดียวกันทั้งใน DB (org_ok()) และ client (orgOk())
  • องค์กร Demo Estate มีทรัพย์ตัวอย่างทุกประเภทไว้ให้ลูกค้าใหม่ดูเป็นแนวทาง
⚠️ การลบองค์กรจะลบทรัพย์ทั้งหมดแบบ cascade — กู้คืนไม่ได้

5. ระบบทรัพย์ (หัวใจของแอป)

5.1 การลงทรัพย์ — ฟอร์มปรับตามประเภท

ฟอร์มเป็นขั้นตอน (step) และช่องข้อมูลเปลี่ยนตามประเภททรัพย์ เช่น โกดัง/โรงงานถามเรื่องเครน ความสูงอาคาร รถคอนเทนเนอร์เข้าได้ · บ้าน/คอนโดถามห้องนอน เฟอร์นิเจอร์ เครื่องใช้ไฟฟ้า · ที่ดินถามไร่-งาน-ตร.วา ผังสี (พร้อมแถบสีตัวอย่าง) FAR/OSR

  • ที่ตั้ง: บ้านเลขที่ (คอนโดเป็น "เลขที่ห้อง" · ที่ดินเปล่าไม่มีช่องนี้) + จังหวัด → เขต → แขวง เป็น dropdown ต่อเนื่องกัน + ปักหมุดแผนที่/ใช้ตำแหน่งปัจจุบัน/วางพิกัด lat,lng ช่องเดียว
  • ผู้ติดต่อ: สถานะเจ้าของ (เจ้าของตรง/ตัวแทน) ชื่อ บริษัท เบอร์โทร เลขโฉนด
  • รูปภาพ: อัปโหลดหลายรูป — ระบบบีบอัดอัตโนมัติฝั่งเครื่องผู้ใช้ก่อนอัปขึ้น Storage (ไฟล์เล็กลง คุณภาพคงเดิม)
  • เอกสารแนบ: โฉนด สัญญา ฯลฯ แยกจากรูปภาพ
  • ราคา: ค่าเช่า/เดือน หรือราคาขาย + ภาษี ค่าธรรมเนียม ค่าส่วนกลาง ค่าน้ำ-ไฟ
  • สถานะดีล: ว่าง / เช่าแล้ว / ขายแล้ว — ใช้กรองในหน้ารายการ

5.2 หน้ารายการและรายละเอียด

  • หน้ารายการ (List) — ค้นหา + กรองตามประเภท/ลงประกาศ/สถานะดีล/จังหวัด/ช่วงราคา · การ์ดบนมือถือมีแถบปุ่มลัด โทร/SMS/แผนที่/แก้ไข
  • หน้ารายละเอียด (PropertyDetail) — แสดงทุกฟิลด์ที่มีข้อมูล · ฟิลด์สำคัญ (ชื่อเจ้าของ เบอร์โทร คนลงข้อมูล บ้านเลขที่) แสดงเสมอ ถ้าว่างขึ้น "ไม่ได้ระบุ" · บทบาทที่ถูกปิดข้อมูลติดต่อจะเห็นแถบ 🔒 "ปิดตามสิทธิ์ของบทบาทคุณ" พร้อมชื่อ-เบอร์คนลงข้อมูลให้ติดต่อแทน · ปุ่มแก้ไข/ลบขึ้นเฉพาะเมื่อบทบาทมีสิทธิ์กับทรัพย์แถวนั้น
  • นำข้อมูลออกเป็น Excel — เฉพาะบทบาท owner (มี can_export() คุมฝั่ง DB คู่กัน)
  • หน้าแผนที่ (Map) — ปักหมุดทรัพย์ทั้งหมดบน Leaflet
  • เปรียบเทียบ (Compare) — เลือกทรัพย์หลายรายการวางเทียบเป็นตาราง
  • นำเข้า Excel/CSV — จับคู่คอลัมน์อัตโนมัติ + insert เป็นก้อน (แพ็กเกจ Pro)

5.3 การมองเห็นทรัพย์และการปิดข้อมูลระดับฟิลด์

ทรัพย์ทุกแถวจดว่าใครลง (created_by) — การมองเห็นตัดสินจากบทบาท 8 ระดับ (หัวข้อ 3.3): เห็นทั้งองค์กร / เฉพาะเขตที่กำหนด (temporary) / เฉพาะที่ตัวเองลง (trainee) · กติกาบังคับที่ RLS: เห็นไม่ได้ = อ่าน/แก้/ลบไม่ได้เลย

การปิดข้อมูลระดับฟิลด์ (masking): บทบาทที่ถูกปิดข้อมูลติดต่อเจ้าของหรือพิกัด ไม่ได้แค่ซ่อนใน UI — ฝั่งแอปอ่านทรัพย์จาก view properties_view ซึ่งปิดค่าคอลัมน์นั้นเป็น null ตั้งแต่ฐานข้อมูล และตาราง properties ถูกถอนสิทธิ์ select ออกจากผู้ใช้ทั่วไป (กันเรียก REST ตรงแล้วเห็นข้อมูลที่ปิดไว้) · การเขียนยังเขียนที่ตารางตามเดิม · view ส่งธง contact_masked/location_masked มาให้ UI แสดงแถบ 🔒

ที่นั่งทีม (seats) และการซื้อที่นั่งเพิ่ม

  • 1 ที่นั่ง = 1 บัญชีในองค์กร (นับเจ้าของ/ผู้จัดการด้วย) — โควตาแถมตามแพ็กเกจ×ระดับ ตามตารางข้างบน · ช่วงทดลองได้ตามแพ็กเกจที่ทดลอง
  • ซื้อที่นั่งเพิ่มได้รายที่นั่ง (ค่าเริ่มต้น 290 บาท/ที่นั่ง/เดือน · รายปี ×12 ลด 15%) ที่หน้า /upgrade#seats — บวกทับโควตาแถม เก็บใน organizations.extra_seats + วันหมดอายุของตัวเอง
  • ราคาที่นั่ง super แก้ได้ (app_settings คีย์ seats) — ค่า default ต้องตรงกัน 3 ที่: api/_lib/seats.js, src/lib/payments.ts, supabase/seats.sql
  • ฐานข้อมูลบังคับจริงผ่าน plan_base_seats()/org_seat_limit() ใน RPC เชิญ/รับสมาชิก · หน้า Team อ่านผ่าน RPC my_seat_usage
  • ⚠️ แพ็กเกจลดชั้นหรือที่นั่งเสริมหมดอายุ = เชิญเพิ่มไม่ได้เท่านั้น — ไม่เตะใครออกจากองค์กร
  • รายปีลด 15% (ราคาเดือน × 12 × 0.85)
  • ระดับโควตา (tier) เก็บที่ organizations.plan_tier (100/250/500 · null = ลูกค้าเก่า ตีความเป็น 500)
  • ทดลองใช้ (trial): องค์กรใหม่ได้สิทธิ์ Pro ชั่วคราวตามที่ super ตั้งไว้ — หมดแล้วยังไม่จ่ายจะล็อกองค์กรจนกว่าจะเลือกแพ็กเกจ
  • ลำดับการตีความสิทธิ์ (effectivePlan): จ่ายเงินอยู่ > trial ที่ยังไม่หมด > free — ตรรกะเดียวกันทั้ง SQL และ src/lib/plan.ts
  • บังคับโควตาจริงที่ DB: trigger enforce_property_limit กัน insert เกินลิมิต (Free 5 · Basic/Pro ตาม tier · trial 500) — ฝั่งหน้าเว็บแค่เตือนก่อนถึงฟอร์ม
  • ราคาแก้ได้จากหน้า Super Admin เก็บในตาราง plan_prices — มีค่า default สำรองใน 3 ที่ที่ต้องแก้ให้ตรงกัน: api/_lib/prices.js, src/lib/payments.ts, supabase/plan-tiers.sql
  • Referral: ชวนเพื่อนสมัคร — คนชวนได้ Pro ฟรีตามเงื่อนไขที่ super ตั้งค่า

7. การชำระเงิน (PunPay — PromptPay)

ผู้ใช้เลือกแพ็กเกจ+ระดับ+รอบบิล→ api/create-charge.js สร้าง QR→ ผู้ใช้สแกนจ่าย→ punpay-webhook.js รับผลจาก PunPay→ RPC apply_payment เปิดแพ็กเกจ
  • ราคาคำนวณฝั่งเซิร์ฟเวอร์เท่านั้น (อ่านจาก plan_prices → fallback api/_lib/prices.js) — client ส่งแค่ plan/tier/billing มา ปลอมราคาไม่ได้
  • webhook ตรวจลายเซ็นจาก PunPay ด้วย PUNPAY_SECRET_KEY ก่อนเชื่อผล
  • มี verify-charge.js ให้หน้าเว็บ poll เช็คสถานะ — เป็นตาข่ายสำรองถ้า webhook มาช้า
  • apply_payment บันทึกลงตาราง payments + อัปเดตแพ็กเกจ/วันหมดอายุขององค์กรเป็นทรานแซกชันเดียว
  • โหมดทดสอบ: สวิตช์ payment_test ใน app_settings + env PUNPAY_TEST_AMOUNT (ต้องปิด/ลบก่อนเปิดตัวจริง)

8. ทีมและการเชิญลูกทีม

  • แอดมินเชิญได้ 2 ทาง: สร้างลิงก์เชิญ ส่งเองทางไหนก็ได้ หรือส่งอีเมลอัตโนมัติ (ผ่าน api/send-invite.js)
  • คำเชิญสร้างผ่าน RPC create_team_invite — ตรวจสิทธิ์ + โควตาที่นั่ง ในตัว → ได้ token ในตาราง team_invites (คำเชิญระบุบทบาทได้ ค่าเริ่มต้น manager)
  • ผู้ถูกเชิญเปิดลิงก์ /#/login?invite=… — สมัครหรือล็อกอินด้วยอีเมลที่ถูกเชิญ แล้วกดยอมรับเข้าทีม
  • แอดมินสร้างบัญชีให้ลูกทีมตรงๆ ก็ได้ (api/create-member.js ใช้ service role สร้าง user ยืนยันแล้วทันที ไม่ติดลิมิตอีเมล)
  • หน้า Team: เปิด/ปิดการใช้งานสมาชิก · ตั้งบทบาท 8 ระดับต่อคน · กำหนดเขต (จังหวัด/อำเภอ) ให้ survey/temporary · เห็นจำนวนที่นั่งที่ใช้/เหลือ พร้อมลิงก์ซื้อที่นั่งเพิ่ม

10. การแจ้งเตือน

  • ช่องทาง: Web Push เท่านั้น (ยังไม่มี LINE bot) — ผู้ใช้กดอนุญาตรับแจ้งเตือน เครื่องถูกจดในตาราง device_tokens
  • ตัวส่ง: api/push-cron.js ถูกเรียกตามเวลา (Vercel Cron) — กวาดหาเรื่องที่ต้องแจ้งแล้วยิง push
  • สัญญาเช่าใกล้หมด: แจ้งล่วงหน้าตามเกณฑ์ (มาตรฐาน 60 และ 30 วัน) — แอดมินแต่ละองค์กรตั้งเกณฑ์เองได้ (organizations.contract_alert_days) ไม่ตั้งใช้ค่ากลางจาก app_settings
  • นัดติดตามถึงกำหนด: แจ้งเจ้าของนัด
  • ในแอปมือถือใช้ Capacitor Push Notifications (FCM)

11. Super Admin

  • หน้า /super: เห็นทุกองค์กร — เปลี่ยนแพ็กเกจ/ระดับ/วันหมดอายุ ระงับองค์กร ตั้งราคาแพ็กเกจ (plan_prices) ตั้งค่า trial/referral/โหมดทดสอบจ่ายเงิน/เกณฑ์เตือนสัญญาค่ากลาง/ช่องทางติดต่อ (LINE OA, โทร, อีเมล — ไปโชว์ที่ landing page) และเปิด-ปิดปุ่มรีวิว
  • สวมสิทธิ์ (impersonate): เข้าไปเห็นระบบเหมือนเป็นสมาชิกองค์กรนั้นจริง (จดใน profiles.impersonate_org_id) — ใช้ช่วยลูกค้าแก้ปัญหา
  • หน้า /superstats: Dashboard ยอดสมัคร realtime — องค์กรทั้งหมด ผู้ใช้รวม จ่ายเงินอยู่/ทดลอง/ฟรี MRR โดยประมาณ กราฟสมัครใหม่รายเดือน 12 เดือน องค์กรล่าสุด 10 ราย (Realtime + polling 60 วิ)

16. ความปลอดภัย

  • RLS เป็นด่านจริง: สิทธิ์ทุกอย่างบังคับที่ฐานข้อมูล — ต่อให้เรียก API ตรงด้วย anon key ก็เห็น/แก้ได้เท่าที่ policy อนุญาต
  • งานที่ต้องข้าม RLS ใช้ RPC แบบ SECURITY DEFINER ที่ตรวจสิทธิ์เองในฟังก์ชัน (เช่น switch_org, create_team_invite, apply_payment, claim_device_session, org_member_names, my_seat_usage)
  • การปิดข้อมูลระดับฟิลด์ปิดจริงตั้งแต่ DB: ตาราง properties ถูกถอนสิทธิ์ select — ผู้ใช้อ่านได้เฉพาะผ่าน view properties_view ที่ปิดข้อมูลติดต่อ/พิกัดตามบทบาท ต่อให้เรียก REST API ตรงก็เห็นเป็น null
  • ความลับอยู่ฝั่งเซิร์ฟเวอร์เท่านั้น: SUPABASE_SERVICE_ROLE_KEY, PUNPAY_SECRET_KEY, AI_API_KEY, SMTP — เก็บใน Vercel env ไม่เคยลง repo/client
  • .env / .env.local ถูก gitignore — client มีแค่ URL + anon key ของ Supabase
  • ราคา/โควตาตัดสินที่เซิร์ฟเวอร์: create-charge คำนวณราคาเอง, trigger กันเพิ่มทรัพย์เกินลิมิต, RPC ตรวจ admin ก่อนเชิญสมาชิก
  • webhook ตรวจลายเซ็น ก่อนเชื่อผลการจ่ายเงิน · trigger ฝั่ง DB ยกเว้น service_role เพื่อให้ระบบหลังบ้านทำงานได้
  • ล็อกอินทีละเครื่อง ลดการแชร์บัญชีใช้งานพร้อมกัน

17. การ Deploy และงานดูแลระบบ

  • เว็บ: push ขึ้น GitHub (branch main) → Vercel build + deploy อัตโนมัติ → แอปมือถือได้ของใหม่ตามผ่าน live-update
  • ฐานข้อมูล: รันสคริปต์จาก supabase/*.sql ใน SQL Editor — ต้องรันก่อน deploy โค้ดที่พึ่งพาสคริปต์นั้น
  • ตรวจก่อน push: npx tsc -p tsconfig.app.json --noEmit && npx vite build + สคริปต์ทดสอบใน scripts/ (Playwright)
  • เปลี่ยน env ใน Vercel → ต้องกด Redeploy ถึงจะมีผล
  • เช็คลิสต์ก่อนเปิดตัวจริง: ลบ env PUNPAY_TEST_AMOUNT + ปิดสวิตช์ payment_test · ลบแพ็กเกจทดสอบ ฿1 · กรอกช่องทางติดต่อจริง (LINE OA/โทร/อีเมล) ในหน้า Super Admin
  • วัดผล: Vercel Speed Insights (ความเร็ว Core Web Vitals) + Web Analytics (ยอดเข้าชม) — เฉพาะเว็บ production
เอกสารภายในทีม HOP — สร้างจากโค้ดจริงของระบบ · ไฟล์นี้อยู่ที่ docs/SYSTEM.html อัปเดตได้เมื่อระบบเปลี่ยน
